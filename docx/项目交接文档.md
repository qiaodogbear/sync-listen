## 1. 项目概述

Sync Listen 是一个 Android 多人同步听歌原型。用户加入同一房间后共享播放列表，
各设备下载并校验相同的 MP3/FLAC 文件，然后在本地播放。Host 统一执行播放、暂停、
seek 和下一首操作，客户端通过服务器时钟、计划执行时间、周期 `SYNC`、seek 和轻微
变速修正实现大致同步。

系统支持两种部署方式：

1. **电脑后端模式**：Windows 电脑运行 Node.js/Fastify 后端，手机通过局域网访问。
2. **手机托管模式**：一台 Android 手机运行内嵌 Ktor/CIO 服务，其他手机通过同一
   Wi-Fi 或 Host 手机热点加入，不需要电脑或互联网。

当前项目是可信局域网原型，不具备公网生产系统需要的账号体系、TLS、细粒度认证、
速率限制和高可用能力。

## 4. 当前架构与数据流

```text
Compose UI
  -> ViewModel / Controller
  -> Retrofit REST + OkHttp WebSocket
  -> RoomRepository
  -> WorkManager 下载队列 -> Room 缓存索引
  -> PlayerController -> Media3 本地播放

电脑模式：
  Fastify -> SQLite + 本地音频目录 + RoomHub

手机托管模式：
  HostServerService -> Ktor/CIO -> HostRoomStore + HostRoomHub
```

### 4.1 电脑后端

- 监听默认地址 `0.0.0.0:3000`。
- SQLite 保存房间、成员、歌曲和播放状态。
- 音频文件存放在 `backend/data/audio`。
- 上传临时文件存放在 `backend/data/tmp`。
- 播放期间由后端周期广播 `SYNC`。

### 4.2 手机 Host

- 前台服务监听 `0.0.0.0:38571`。
- Host 自己通过 `http://127.0.0.1:38571` 访问服务。
- 成员使用 Host 的局域网 IPv4，例如 `http://192.168.43.1:38571`。
- 权威房间状态当前仅保存在 `HostRoomStore` 内存中。
- 音频文件保存在 App 私有目录并按 SHA-256 去重。
- Host 离开、服务停止、进程被杀或手机重启后，当前房间无法恢复。

## 11. 当前已知问题

### 11.1 稳定性

- 手机 Host 的权威房间状态只存在内存中，Host 进程被杀、重启 App 或手机重启后无法恢复。
- `HostServerService` 当前使用 `START_NOT_STICKY`，不会由系统主动重建。
- Host 网络地址变化后，旧邀请中的地址失效；当前没有网络切换状态机或重新发布邀请机制。
- 没有真实手机长时间锁屏、热点和省电策略验收。
- 不支持 Host 迁移、备用 Host 或故障接管。

### 11.2 易用性

- 首页将创建、加入、二维码、BLE、NFC、调试设置全部纵向堆叠，信息层级不清晰。
- 用户需要理解 Host 地址、服务器模式和网络互通，缺少自动连通性诊断。
- 手机热点需要用户自行进入系统设置开启，App 没有步骤化引导。
- 恢复、权限拒绝、网络隔离等故障提示偏技术化，缺少可执行修复按钮。
- 调试字段长期展示在房间主界面，普通用户信息负担较大。

### 11.3 UI 与代码结构

- 大部分 Compose 页面集中在 `SyncListenApp.kt`，文件职责过多，不利于布局迭代和测试。
- 当前 Material3 Theme 几乎使用默认配置，缺少品牌颜色、字体层级、形状、间距和暗色模式设计。
- 房间页面是长列表按钮，缺少固定播放器控制区、歌曲卡片、成员状态组件和清晰导航。
- 上传页、邀请页、设置页仍接近功能占位形态。
- UI 自动化测试和截图回归不足。

### 11.4 安全与工程

- 当前使用明文 HTTP/WebSocket，仅适合可信局域网。
- 房间使用共享 join token，不是独立成员令牌。
- 无账号、持久会话认证、速率限制或上传配额。
- Node.js 24 的 `node:sqlite` 会输出 ExperimentalWarning。
- 开发依赖审计仍报告 high severity 漏洞，生产依赖审计为 0。
- Windows 中文路径需要 `subst S:` 才能稳定运行 Gradle 单测。

## 12. 后续优化路线图

优化顺序已经确定为：**稳定性优先，其次易用性，最后重构布局与 UI 美学**。

### 阶段 A：稳定性与自动恢复

目标：Host 异常退出后不丢失房间，重新打开 App 后可以一键恢复原房间。

建议添加：

- 为手机 Host 新建独立持久化数据库，保存房间、join token、成员、Track、存储路径和播放状态。
- 将 `HostRoomStore` 改为持久化仓库加内存快照，而不是纯内存状态。
- 区分“用户明确关闭房间”和“进程异常中断”：
  - 用户离开或停止托管时永久关闭并删除可恢复标记。
  - 进程异常中断时保留活动房间和恢复标记。
- App 首页增加“恢复上次托管房间”卡片。已确定采用用户再次打开 App 后一键恢复，
  不在手机开机时静默后台启动。
- 恢复前重新解析当前可达 IPv4；地址变化时生成新邀请并提示成员使用新地址。
- 恢复时将所有历史成员标记为离线，等待 WebSocket 重连后恢复在线状态。
- 播放状态恢复为暂停状态，并保留当前曲目和位置，避免后台恢复时突然播放。
- 增加服务心跳、网络变化监听、端口检测和结构化错误状态。
- 完成真实手机锁屏、热点、Wi-Fi 切换、系统杀进程和重启 App 验收。

验收标准：

- Host 进程被系统终止后重新打开 App，首页显示原房间恢复卡片。
- 点击恢复后沿用原房间码、播放列表和文件，当前曲目保持暂停。
- 网络地址改变时显示新地址，旧成员获得清晰的重新加入提示。
- 用户明确关闭后不再显示恢复卡片。

### 阶段 B：易用性与连接引导

目标：普通用户无需理解服务器地址或调试概念即可创建和加入房间。

建议添加：

- 首页改成两个主入口：“创建房间”和“加入房间”，默认推荐手机托管。
- 创建流程使用步骤式引导：
  1. 检查昵称。
  2. 检查 Wi-Fi/热点与可达地址。
  3. 检查通知和附近设备权限。
  4. 创建并显示邀请。
- 加入流程优先展示附近房间和扫码；手动地址放入“高级方式”。
- 增加 Host `/health` 连通性探测，并将错误分类为：
  - 不在同一网络。
  - Host 已停止。
  - 地址不可达或端口被阻止。
  - 房间码无效或房间已关闭。
- 每类错误提供具体操作按钮，例如“重新检测”“打开 Wi-Fi 设置”“重新扫描”。
- 增加系统设置跳转，引导用户开启热点、关闭省电限制或授予通知权限。
- 将技术调试字段移入可折叠“诊断信息”面板。
- 保存最近昵称、最近加入方式和最近可恢复房间，但不保存过期加入令牌到日志。

验收标准：

- 新用户只通过主入口和引导即可完成创建与加入。
- 正常流程无需手动输入 Host IP。
- 常见连接失败能显示原因和下一步操作。

### 阶段 C：界面布局与 UI 美学

目标：从功能验证页面升级为结构清晰、适合日常使用的音乐房间界面。

建议设计方向：

- 使用 Material 3，并建立 Sync Listen 视觉系统：
  - 深色优先，同时支持浅色模式。
  - 音乐主题强调色、统一圆角、间距和 elevation。
  - 明确标题、正文、辅助信息和错误状态层级。
- 拆分 `SyncListenApp.kt`，每个页面、组件和导航职责独立。
- 首页：
  - 顶部品牌区域。
  - “创建房间”“加入房间”两个主要卡片。
  - 可恢复房间卡片。
  - 最近房间和网络状态。
- 房间页：
  - 顶部房间信息与在线成员头像。
  - 中部播放列表卡片。
  - 底部固定迷你播放器与 Host 控制栏。
  - 上传、邀请和设置放入顶部操作或底部导航。
- 邀请页：
  - 二维码为视觉中心。
  - 显示网络状态、房间码、分享和附近邀请状态。
